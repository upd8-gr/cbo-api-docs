# API changelog

## v1.1

- 2026-11-03: **Breaking** — `POST /supplier-invoices`: `is_self_issued` now selects between *registering a purchase* (`false`, the default when omitted) and *issuing our own document* (`true`). When registering, `invoice_type_id` / `document_id` and `invoice_series_id` are refused with 422 (`"invoice_type_id is only accepted when is_self_issued is true."`, `"invoice_series_id is only accepted when is_self_issued is true."`) and `mydata_submit: true` is refused with 422 (`errors.mydata_submit`: `"Registered supplier invoices cannot be submitted to myDATA."`). Callers that send our invoice type must add `is_self_issued: true`. Applies to `invoice`, `credit-invoice`, `delivery-note`, `delivery-return`, `delivery-internal`; `cash-receipt`, `return` and `retail` are unaffected.
- 2026-11-03: **Breaking** — `GET /supplier-invoices`, `GET /supplier-invoices/{id}`, `POST /supplier-invoices` and the `/supplier-payments` endpoints (same response): `invoice_series_id` is now the id of our series and appears only on issued documents with a series; it used to carry the stored series text, which on registered purchases was the counterparty's free-text series. That text is now returned in the new `invoice_series` key. `invoice_series_id` and `serial_number` are still omitted when null.
- 2026-11-03: **Breaking** — `GET /invoices`, `GET /invoices/{id}`, `POST /invoices`, `POST /invoices/{id}/publish`: a linked `delivery-note` or `delivery-return` is now listed under `delivery_notes` and no longer under `related_documents`, whichever key it was sent in. Receipts, returns, credit invoices, `delivery-centralized` and `delivery-internal` links stay in `related_documents`.
- 2026-11-03: **Breaking** — `POST /invoices/{id}/publish`: an invoice in any status other than `Draft` or `Executed` (e.g. `Pending`) now returns 422 `business_validation_error` `"Only draft invoices can be published (current status: Pending)."`; it used to return 200 and leave the document unchanged.
- 2026-11-03: **Breaking** — `POST /invoices/{id}/publish` and `POST /invoices` (when it publishes): the "serial number already used" error moved from the key-less `errors[0][0]` (`"Ο αριθμός του Παραστατικού δεν είναι έγκυρος."`) to `errors.serial_number` with the text `"Ο σειριακός αριθμός δεν είναι έγκυρος, γιατί υπάρχει ήδη."`. A hand-typed `serial_number` is now refused whenever an issued or cancelled document already holds it in the same numbering scope (company, branch, series, myDATA type), including documents never sent to myDATA. The same check applies to documents issued through `POST /supplier-invoices` and `POST /supplier-invoices/{id}/publish`.
- 2026-11-03: **Breaking** — `POST /invoices/{id}/publish` and `POST /invoices` (when it publishes): a line of a serial-tracked product with fewer serial numbers than its quantity is refused with 422 (same rule as the web form; it used to publish).
- 2026-11-03: **Breaking** — `POST /invoices/{id}/publish` and `POST /invoices` (when it publishes): the 350-line limit message is now `"Ο αριθμός των ειδών υπερβαίνει το όριο (350). Παρακαλώ χωρίστε το παραστατικό."`.
- 2026-11-03: **Breaking** — `POST /invoices`: an id of another company's document in `related_documents` / `delivery_notes` is refused with 422 (`errors.related_documents.N` / `errors.delivery_notes.N`); it used to be accepted.
- 2026-11-03: **Breaking** — `POST /invoice-types`: `aade_type` is validated against the codes allowed for the resulting `document_type` (see the request schema), with a single message under `errors.aade_type`; the second message `"Invalid AADE type for selected type."` is gone. Some legacy combinations changed (e.g. `type` 1 + `1.4`, `type` 3 + `9.2` / `11.1` are refused; `type` 3 + `9.1` is accepted). The deprecated `type` 3 does not derive a document type, so delivery types must send `document_type`. There is now one default type per `document_type` + `account` (was per `type` + `document_type`), and a type created without `account` is a `client` type.
- 2026-11-03: **Breaking** — `GET /invoice-types`, `GET /invoice-types/{id}`, `POST /invoice-types`: the deprecated `type` is now derived from `document_type` + `aade_type` (5 for 7.1 / 8.1 / 8.2 income types, 6 for 3.1 / 3.2, 7 for `retail`; an `invoice` with an 11.x code is 1), and `document_type` is always present.
- 2026-11-03: `POST /supplier-invoices/{id}/publish` — new endpoint: publishes a `Draft` supplier invoice, or with `mydata_submit: true` retries the myDATA transmission of an `Executed` one we issued.
- 2026-11-03: `POST /supplier-invoices` — new request fields `is_self_issued`, `representation` (free-text name of a registered purchase; prohibited when issuing) and `invoice_series` (counterparty's free-text series; prohibited when issuing). New response keys `is_self_issued` (always present), `invoice_series` and `dispatch_detail`. `isDraft: true` now stores the invoice as `Draft` (it was stored `Executed`). A myDATA rejection returns 422 `business_validation_error` and stores nothing (it was a 500). `document_type: cash-register` is accepted and stored as `retail`.
- 2026-11-03: `POST /invoices` — `document_type: cash-register` is accepted again and stored as `retail`; `invoice-income` and `accommodation-income` are accepted, and an `invoice` posted with a 7.1 / 8.1 / 8.2 type is created under the matching income document type. Documented the existing `document_id`, `billing_address_id`, `shipping_address_id`, `loading_address_id` fields. `GET /invoices` and `GET /supplier-invoices` accept `cash-register` / `cancel-register` as `document_type` filters (matched as `retail` / `credit-retail`).
- 2026-11-03: `POST /invoices/{id}/publish` — `Executed` + `mydata_submit: true` retries the myDATA transmission only (no new number, receipts or stock movement); an invoice that already holds an active MARK is refused with 422 and not sent again. With `mydata_submit: true` a company without myDATA settings now gets the invoice published without sending (it was a 500).
- 2026-11-03: `GET /invoice-types` — new response fields `account`, `dispatch_details_enabled`, `dispatch_policy`, `has_billing`, `only_clients`, `default_move_purpose`; new filters `account` and `dispatch_details_enabled`; the deprecated `type` filter takes one value or an array of 1–7 and matches the derived `type`; `sort_by` accepts `type`, `account`, `dispatch_details_enabled`. `type` and `is_deliverable` are marked deprecated (request and response); when `type` and `document_type` are both sent, `document_type` wins; when `is_deliverable` and `dispatch_details_enabled` are both sent, `dispatch_details_enabled` wins. `POST /invoice-types` accepts `account` and `default_move_purpose`.
- 2026-11-03: `PUT /invoice-types/{id}` / `PATCH /invoice-types/{id}` — new endpoint (full payload on both).
- 2026-11-03: `POST /groups` — documented: `sort` omitted, null or `0` on create places the group at the end of its siblings.
- 2026-11-03: Docs corrections — `payment_way` on invoice and supplier invoice responses is a slug (`cash`, `bank`, …), not the stored label; error responses of `POST /invoices/{id}/publish` and `DELETE /invoice-types/{id}` use the `{status,message,errors}` envelope.
- 2026-07-27: `GET /product-children` — added `on_website` boolean query parameter (filters product children by whether the product is shown on the website) and `on_website` boolean field to the product child response schema.
